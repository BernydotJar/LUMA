### Threat

Original GitHub issue #61: coach with trusted tenant membership but no assigned offering was not listed as an instructor for the program yet could read all program-level learner evidence. The entrypoint was GET `/api/coach/learners/:learnerId` with `x-luma-program-id`; also applicable to roster and interventions. Cross-tenant denial already functioned. Root cause was `access.tenantIds.includes(scope.tenantId)` being used as an evidence grant rather than a membership prerequisite.

### Fix and independent checks

- The same server-derived active offering policy controls course listing and every entitled coach data route.
- `coachTenantIds` is membership, not the final permission; institutional admin scope uses `adminTenantIds` and superuser remains platform-wide.
- An active course assignment is refreshed from Firestore on every read. A coach must be assigned to **every active or historical cohort** of a program because the evidence store is currently only tenant/program scoped, not cohort scoped.
- Archiving an unrelated cohort does not grant access to its historical program-level evidence. An instructor must be explicitly assigned to every historical offering as well, pending cohort-scoped Twin support (#63).
- The authorized `offeringId` list is generated by the server after checking assignments; enrollment requires that exact current offering ID. Plain token claims and local storage cannot impersonate this list.
- HTTP Auth/Firestore Emulator journey verifies 16 distinct checkpoints, including 401/403, same-tenant negative cases on three endpoints, authorized admin reads, rerouting assignment, live revocation, active and archived partial-cohort fail-closed, 101-offering capacity fail-closed (409), unrelated tenant denial, server evidence reload, learner revoke.
- No genuine Hotmart sales, customer users or production Firebase data. Emulators discarded synthetic records and revoked the synthetic test identities. No production permission changes.
